# Domain Docs

How the engineering skills should consume this repo's domain documentation when exploring the codebase.

## Before exploring, read these

The repo keeps its memory in three places. Read them in this order, and prefer
them to crawling the tree:

1. **`FILE-MAP.md`** at the repo root — **layout**. Every directory's purpose and
   every source file's one-line purpose, grouped by layer (ingest → seam →
   gateway → web → tooling → docs → data). Start here to answer "which file do I
   open?" It is generated by `scripts/gen_file_map.py` and CI-gated, so it cannot
   go stale: directory purposes live in that script's `DIRS` table, and file
   purposes are read out of each file's own header comment or docstring.
2. **`CONTEXT.md`** at the repo root — **vocabulary**. The glossary every issue,
   ADR and identifier is expected to use.
3. **`docs/adr/`** — **decisions**. Read the ADRs that touch the area you're
   about to work in.

`docs/agents/*.md` (this file and its siblings) is the **how-to** layer: the
conventions for issues, triage and domain docs.

### Keeping the map honest

- Adding a directory? Add a row to `DIRS` in `scripts/gen_file_map.py` — `--check`
  fails if a directory has no entry, so new folders can't appear undocumented.
- Adding a source file? Give it a one- or two-line header comment saying what it
  is for. That header *is* its row in the map.
  - Go: a plain `// …` comment at the top, then a **blank line**, then the
    `package` clause — the blank line keeps `go doc` reading the real package
    doc rather than your file comment.
  - Python: a module docstring. TypeScript/JS: a `//` or `/** */` header.
    Dockerfiles/YAML/ini/requirements: a leading `#` comment. Markdown: YAML
    front-matter `description:`, or a leading `<!-- … -->` comment.
- Then run `python scripts/gen_file_map.py`.

If any of these files don't exist, **proceed silently**. Don't flag their absence; don't suggest creating them upfront. The producer skill (`/grill-with-docs`) creates them lazily when terms or decisions actually get resolved.

## File structure

Single-context repo:

```
/
├── FILE-MAP.md          generated layout index — read first
├── CONTEXT.md           glossary
├── docs/adr/            decisions
│   ├── 0001-example-decision.md
│   └── ...
├── docs/agents/         how-tos (this file)
└── src/
```

## Use the glossary's vocabulary

When your output names a domain concept (in an issue title, a refactor proposal, a hypothesis, a test name), use the term as defined in `CONTEXT.md`. Don't drift to synonyms the glossary explicitly avoids.

If the concept you need isn't in the glossary yet, that's a signal — either you're inventing language the project doesn't use (reconsider) or there's a real gap (note it for `/grill-with-docs`).

## Flag ADR conflicts

If your output contradicts an existing ADR, surface it explicitly rather than silently overriding:

> _Contradicts ADR-0007 (example decision) — but worth reopening because…_
